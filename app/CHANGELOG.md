# Changelog

All notable changes to the `zzmq` package (the `zz` CLI) are recorded here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning follows [semver](https://semver.org/).

## [Unreleased]

### Added
- **Charter, built for real** (closes [#55](https://github.com/zzmq-dev/zz/issues/55)): a plain `CHARTER.md` tracked on a repo's `zz-meta` branch, read with a new `readCharter` helper (`cli/lib/repo.ts`) via ordinary git (`git fetch` + `git show`) -- no new tool, no new API surface, matching the explicit decision for Charter's storage. Wired into `changeset_review`'s system prompt and prompt assembly first (not grooming, which doesn't exist as real code yet -- blocked on [#53](https://github.com/zzmq-dev/zz/issues/53)): read fresh on every review, by whichever agent happens to be reviewing, not cached or read once by a privileged role -- the corrected, ambient-consultation design, not the retracted standing-ask one. A review now has two genuinely separate rejection reasons available (doesn't match the task vs. doesn't belong at all), closing the exact gap the `gcd`-duplicate and `median`-touching-`index.js` triage incidents found live. Verified end to end against the real deployed Worker: `readCharter` correctly returns `null` before a Charter exists and the real pushed content after, with no Worker deploy needed since the read path is pure client-side git.

- **Insights, built for real** (closes [#8](https://github.com/zzmq-dev/zz/issues/8)): a `norm` observed or a `trap` found, postable via a new `insight_post` tool, searchable via `ladder_search` with `trap`-kind results boosted over an equally-relevant ordinary summary (SQLite BM25 multiplier remotely, a stable sort locally). Reuses the existing repo-wide-anchor machinery `ask`/`contributor`/`dependencies` already have (`insight_norm`/`insight_trap` added to `RungKind`) instead of inventing a parallel storage system -- the only genuinely new storage code is the ranking boost itself. `engine/lane.ts`'s existing `postInsight` (previously Lane-history-only, used only by the incident runbook) now also writes to the Ladder, so a trap found during incident response is discoverable by an unrelated future agent too, not just whoever reads that one Lane's own history. The denial that caps a repeatedly-failing review retry chain (`needsTriage`) now also posts a `trap`-kind Insight automatically, so the failure is informative beyond the one task it happened to.
  - Real bug caught and fixed while verifying this live, not found by inspection: the remote (Cloudflare) backend's `ask`/`directory`/`contributor`/`dependencies` kinds all share one `code` git-notes ref *and* the same anchor oid (the repo's root commit) -- safe only because they're written exactly once, as a complete batch, during onboarding. Insights are posted incrementally, one at a time, throughout a Lane's ongoing life -- writing one through that same shared slot would have silently overwritten whatever was already there (quite possibly `_repo`'s own rung), since `git.addNote`'s `force: true` replaces rather than merges. Fixed by giving insight kinds their own path-keyed ref remotely, matching what the local backend already did safely for this exact class of item. Verified live against the real deployed Worker: `_repo`'s own summary confirmed byte-identical before and after posting two Insights, both Insights correctly added as new children, both independently readable by their own path.

### Fixed
- Closes [#28](https://github.com/zzmq-dev/zz/issues/28). Two more real concurrency races found while re-verifying the issue's already-shipped worktree-isolation fix with a fresh live reproduction (5 concurrent processes against a repo neither had cloned locally yet): (1) `ensureCloned`'s initial clone had no protection at all -- every concurrent caller saw the target directory didn't exist yet and ran `git clone` straight into it, so only the first one could actually create it; every other one hard-failed with `fatal: could not create work tree dir: File exists`. Fixed by cloning into a uniquely-named temp directory first, then atomically renaming into place -- a loser's own (fully valid, just unlucky) clone is discarded in favor of whichever one won the rename, rather than erroring. (2) `disableFetchNegotiation`'s `git config` call raced on git's own config lockfile when multiple callers hit it concurrently -- fixed by running it against the exclusive temp directory before the rename (so it travels with whichever clone wins and never contends in the clone path), plus a short synchronous retry (`Atomics.wait`-based, no subprocess spawn) for the pre-existing "already cloned" branch, where multiple callers can still legitimately hit the same already-shared directory at once. Verified with 20 real concurrent-process runs across 4 batches (fresh clone x3, already-cloned x1), 0 failures after the fix, reproducible failures before it. The "shallow clones per operation" idea from the issue's own first comment is superseded, not implemented: the shipped design (one full-depth shared base clone + a worktree per operation) never needs per-operation depth variance, since every worktree already has full access to whatever the shared base has fetched.

### Changed
- Retired "Maintainer" from user-facing vocabulary entirely -- survives only as `MaintainerDO`'s class name, an implementation detail. The repo-level Role is now **Coordinator** (`RbacRole`/`Role`: `"owner" | "coordinator" | "contributor" | "viewer"/"reader"`). A Lane's `maintainers` list is retired too, not just renamed: `changeset_review` moved to `open` ASK_SCOPE (any Agent may submit a review opinion -- Policy's existing approval mode, not list membership, decides what's sufficient to merge), and the list's remaining real job (Committee voting on `vote_request`) is now `committee`, matching the ASK_SCOPE value it was already checked against. `grantLaneRole`'s `as` parameter, `lane_propose`/`lane_grant`'s payloads, and `zz work --scope` all follow (`--scope maintainer` -> `--scope committee`, now meaning "merge and voting, never open-scope work" since review moved into the open bucket). A real pre-existing bug caught incidentally while touching this: `zz review`'s claim-granting fallback used `lane.maintainers[0]` to satisfy a *coordinator*-scope RBAC check, which only worked because that list defaulted to the same set as `coordinators` -- fixed to read `lane.coordinators[0]` directly. Existing persisted Lanes (local SQLite and the deployed Worker's Durable Objects) have the old `maintainers` key baked into their stored JSON; a read-time migration (`migrateLane`, applied at every Lane read path in both backends) fills `committee` from legacy `maintainers` the first time an old Lane is read, so nothing silently breaks on upgrade.

### Added
- Fixed a real, likely-explains-it bug behind "only tests, never the implementation" submissions repeating across many retries: neither `openaiCompatBackend.ts` (Groq, Cloudflare Workers AI) nor `ollamaBackend.ts` ever checked whether a streamed chat response actually reached its real completion signal (`[DONE]` for the OpenAI-compatible SSE protocol, `done: true` for Ollama's NDJSON) before returning. A stream cut off mid-generation -- a dropped connection, a rate limit killing an in-progress response, a local Ollama restart -- just ended the `for await` loop with whatever partial content had accumulated, silently returned as if it were the real, complete answer. Both now throw a clear error instead when the stream ends without its real completion signal, which `generateText`'s own retry (below) now catches and retries rather than accepting the truncated result. Also made that retry's backoff rate-limit-aware: a 429 (detected from the error text, not assumed to be any specific provider's tier) now waits 10s/20s instead of the generic 1s/2s, since a per-minute quota doesn't clear in one second regardless of what the actual limit number is.
- A capped-out changeset_review denial (3 failed attempts, see below) now carries `needsTriage: true` and a `retryChain` (every prior attempt's rejection reason, in order) directly on the deny answer itself, instead of just a log line that's easy to scroll past and impossible to filter for. `zz lane log --needs-triage` finds exactly these, so a human can actually triage what went wrong without manually reconstructing the chain from raw Lane history first.
- A real, atomic fix for two different real actors ("dev1" and "dev3") both successfully claiming the same ask -- confirmed live. The existing "already answered" check inside `answer()`'s atomic transaction only protected one claim_request from being double-answered; it never checked whether a *different* claim_request, targeting the same work ask, had already been granted. Two genuinely distinct actors, each reading "unclaimed" and posting their own claim_request, both got granted. `answer()` now checks `claimHolder` on the target ask inside the same transaction the duplicate-answer check already runs in (relocated from `engine/workqueue.ts` to `engine/lane.ts`, which needs to call it directly without a circular import; still re-exported from `workqueue.ts` for existing callers) -- whichever grant reaches the transaction first wins, the second now sees the first's effect already committed and is rejected instead of also succeeding. Verified with a real concurrent test using two genuinely distinct identities, not the same one twice: against a fresh Durable Object instance it worked immediately; against an already-warm one it took a second deploy to take effect, since Cloudflare's own "deploying restarts every Durable Object" didn't hold on the first attempt here -- a real operational gotcha worth remembering, not just a one-off.
- A reposted "work" ask, after a changeset_review requests changes, now carries `revises` (the denied changeset_review's own id) and `attempt` -- a real, walkable chain back through the revision history (new work -> revises -> old review -> its own new `taskAskId` -> the work ask before that -> ...), the same shape as a Lane's origin chain or a git commit's parent pointer. Direct fix for "this shouldn't look like a fresh green-field task every time it's rejected" -- the posted `description` stays the same stable text on purpose (so the existing retry count, which matches on it, keeps working), but the ask is no longer a disconnected restatement with no trace of what's already been tried. This is what "the ask becomes a context window for the work" means mechanically: the accumulated history is reconstructable by walking the chain, not crammed into one field.
- A real cap on changeset_review's deny-then-repost cycle: `acceptReview` now counts prior "work" asks in the Lane with the exact same task description (walked from Lane history, not a payload-threaded counter, so it's robust regardless of call path) and stops reposting after 3 attempts, leaving the task denied/blocked for a human to look at instead of retrying forever. Found live: with no check anywhere for whether a task is already satisfied and no limit on repost count, plain model non-determinism in review (not a real bug in the proposed code) was enough to cycle indefinitely -- confirmed live, the same function ("clamp", "mean", "median", "roundTo"...) committed four separate times in a row, open-ask count climbing instead of draining rather than converging. This caps the damage; a smarter fix (checking whether the task is already satisfied before reposting at all) is designed separately as "ask grooming" in [the Ladder-RAG doc](https://zzmq.dev/docs/ladder-rag/).
- `zz login --whoami`: prints the currently logged-in account and the API base it's logged into, without starting a new login. Throws the same "not logged in" error every other credential-requiring command already does if there's nothing to report, rather than printing a soft message and exiting 0 -- a script checking login state via exit code gets the same behavior as any other zz command would.

### Fixed
- Four `git` subprocess calls that ran during a live `zz work` session (`fetchClone`'s fetch, `ensureCloned`'s clone, the `update-ref` that keeps `HEAD` current, and a coordinator's own fetch of a shard's objects before merging) still inherited stdio -- git's own progress/warning text on stderr printed straight to the real terminal, intermittently corrupting the TUI's alternate-screen frame mid-session (self-healing on the next render, but confirmed live, "every so often," running several real workers at once -- `fetchClone` specifically runs on every single claimed ask in remote mode, making it the most frequent source). Same fix `agent/tools.ts`'s `run_in_sandbox` already needed for its own git calls: fully suppressed, piped rather than ignored so a real failure's actual git error text still reaches the thrown error's own `.stderr` instead of being lost. `engine/localBackend.ts`'s own `ensureCloned` had the identical gap for local mode, fixed the same way.
- A transient network failure during a model call (a connect timeout, a dropped connection) could also crash `zz work --stdio` entirely mid-run -- confirmed live, an uncaught "fetch failed / Connect Timeout Error" propagating straight up through the main polling loop. Two layers now: `agent/scriptedWork.ts`'s `generateText` retries up to three times with backoff (1s, then 2s) before giving up, since a flaky connection to a model backend is routine, not a sign anything's actually wrong -- a genuinely persistent failure still throws after exhausting attempts rather than retrying forever silently. And `work.ts`'s `mainLoop` (the unattended, long-running loop specifically -- not the one-off `--ask <id>` path, which should still fail loudly on a real error) now catches whatever's left over from any claimed ask and logs it rather than dying, the same resilience posture the loop already has for "nothing claimable right now." Doesn't retry or release the specific failed ask -- it may sit claimed-but-unfinished, the same open gap [#30](https://github.com/zzmq-dev/zz/issues/30) already tracks for a different trigger -- this just keeps the worker process itself alive to keep serving everything else claimable in the meantime.
- `zz work --stdio` could crash entirely, mid-run, whenever a scripted flow ("work"/"submit_changeset", driven directly by code rather than the generic tool-calling loop) tried to answer an Ask a parallel actor had already resolved a moment earlier -- confirmed live running several real, separately-identified workers against the same queue. `agent/loop.ts`'s generic loop already catches this exact "already answered" signal internally and treats it as benign (the error is tagged `resolved: true` on purpose, specifically for this), but `runWorkAsk`/`runCoordinatorSubmitChangeset` never went through that loop at all, so nothing was catching it for those two ask kinds -- it propagated straight up through the main polling loop and killed the whole process instead of just moving on to the next claimable ask, which is what it always meant. Caught once now, in `work.ts`'s `workClaimed` (the one place every ask kind already funnels through), rather than scattered into each scripted flow individually.
- Two concurrent `zz work` processes against the same repo (same identity or different, each legitimately holding a different claimed Ask) could corrupt each other's local checkout -- confirmed live as `fatal: path '<file>' exists on disk, but not in '<sha>'`, one process's `syncClone` resetting the one shared working tree out from under another's in-progress read. `syncClone` is now `fetchClone`, fetch-only (updates `origin/main`, never resets the shared clone's own working tree -- safe under git's own ref-locking for any number of concurrent callers), and every claimed-ask operation now runs inside its own isolated `git worktree` instead of the shared clone directly, via one unified pathway (`withIsolatedRepo`/`ensureWorktree`/`removeWorktree` in `cli/lib/repo.ts`) that `zz work`'s `workClaimed`, `zz ladder sync`, and `scriptedWork.ts`'s `proposeReview` (changeset_review's sandbox re-verification) all now go through, rather than each hand-rolling the same create-worktree-then-cleanup dance independently -- principle #5, invent as little as possible, applied to this codebase's own internals. `prepareReviewWorkspace` -- the one case that deliberately leaves a checkout on disk for a human to `cd` into afterward -- uses a sibling helper, `ensureNamedWorktree`, keyed by ask id so repeat `--assist` turns on the same ask reuse and fast-forward the same path instead of leaking a new one each time; the two functions' previously-duplicated shard/source_repo resolution is now one shared `resolveReviewTarget`, not two. `fetchClone` also moves the local `main` branch ref to match `origin/main` (a second ref-only update, never touching the working tree) -- without this, `agent/tools.ts`'s `run_in_sandbox` (which independently re-resolves a repo and hardcodes a `"HEAD"` checkout) would have started reading stale content the moment the old reset-based refresh went away; this keeps a plain `"HEAD"` correct everywhere without threading remote-vs-local mode awareness into every caller. Verified with real reproductions, not just reasoned about: 5 concurrent workers hammering one shared clone corrupted 4 of 5 on every run of the old approach, ran cleanly five-for-five on the new one across repeated runs; a simulated remote push confirmed a fresh `"HEAD"` checkout sees it immediately after `fetchClone`, where it previously would have stayed stale.
- `zz ladder push`/`zz ladder sync`'s destination `owner/repo` never resolved `@me` -- found live while bulk-importing real GitHub repos: `zz ladder push <local> @me/<repo>` built a git push URL containing the literal, unresolved string `@me`, failing with a plain "not found" against a destination that, URL-decoded, obviously can't exist. `zz ladder edit`'s slug had the same gap. The two commands' own *source* argument (a GitHub `owner/repo`, not a zz account) is correctly left alone -- `@me` has no meaning there.

## [1.2.0] - 2026-10-15

### Added
- Deleting a repo, or making it private, no longer blocks on or cascades onto its shards: one surviving shard is promoted to take over as the shard tree's new root (fewest commits behind the old origin, ties broken by most recent protocol activity), and every other shard -- regardless of who owns it -- is repointed at the promoted one. Same behavior GitHub itself uses for a deleted/privatized repo's forks. See [Governance](https://zzmq.dev/docs/governance/#deleting-a-repo-or-making-it-private).
- Creating a repo (`zz repo create`), or claiming a `work` Ask (which forks a shard), now auto-tracks it for its creator/claimer -- it shows up in `zz top` immediately, instead of needing a separate manual `zz repo track` first.
- `zz top`/`zz work`'s TUI: the Protocol tab is renamed **Activity** (`zz work`'s old raw-log Activity tab is now **Live feed**, to free up the name), reads newest-first instead of oldest-first, and its row format changes from `[TIME] [REPO] [LANE] [VERB] [KIND] from [USER]` to `[TIME] [VERB] [KIND] on [REPO] [LANE] by [USER]`. Two new entries show as `LANE`, not yet real protocol verbs but displayed as one since they likely will be: `create` (a repo's own creation, via a new `repo_info` tool) and `merge` (the ANSWER that actually completes a `submit_changeset`, today's real merge moment). A deleted repo has no equivalent `LANE delete` yet -- there's no durable record of a deletion to read back once the repo is gone, so this is left for later.
- `zz top`'s Lanes tab: pressing enter on an ask (previously a no-op there, since zz top has nothing to claim) now opens its full contents as pretty-printed, scrollable JSON -- the only place to see a payload in full; the row list itself truncates it to one line.
- `zz review --ask <id>`: reviews one specific changeset_review and exits, instead of the default wait loop -- for a one-off command-line step (a demo's own script, say) rather than a person sitting at a terminal continuously reviewing whatever shows up next.
- `zz review`/`zz work` both gain `--no-wait` (work/review everything currently claimable, then exit once the queue is empty, instead of idling and rechecking forever), and `zz work` gains its own `--ask <id>` (work that one specific ask, any kind/scope, and exit) alongside `zz review`'s existing one. Three modes on each command now: the default wait loop, `--no-wait` to drain and stop, or `--ask <id>` for exactly one known ask -- verified live against the deployed Worker, including that `--ask` leaves every other claimable ask completely untouched.
- `zz repo clone` now sets `pull.rebase true` on every clone, so a later plain `git pull` lands cleanly on the real merged commit instead of refusing (`--ff-only`) or adding a pointless merge commit: `zz repo submit` never pushes your local commit, a coordinator's `commit_changeset` re-commits its content server-side as a different-sha commit, and rebase is the one mode where git recognizes your local commit's patch is already upstream and drops it. Verified live: clone, commit, submit, review, merge, then `git pull` lands exactly on the merged commit with a clean tree. See [Git compatibility](https://zzmq.dev/docs/git-compatibility/#why-zz-repo-clone-sets-pullrebase).
- `zz work --assist` now offers `submit_changeset` asks too, not just `work`/`changeset_review` -- found live by a reader stuck exactly here: an approved review's own merge step was unreachable from the assist view at all. Picking one skips straight to `/merge` (nothing to draft or discuss, the content's already fixed), which runs the exact same mechanics `zz work`'s autonomous loop uses for this ask kind -- a real three-way merge, commit, and Ladder write -- not a separate human-only path. Reports the real outcome (merged, or denied into a `resolve_conflict` ask) rather than assuming success.
- `@me` in any `owner/repo` slug or principal argument now expands to your own logged-in username -- `@me/mathkit`, `@me[claude]` (your own managed agent), `@me[claude]/mathkit[some-task]`. Replaces the demo docs' old `<me>` placeholder, which wasn't just a copy-paste nuisance but a real shell footgun: `<me>/mathkit` gets intercepted by the shell itself as input/output redirection before `zz` ever sees it (confirmed live: zsh reports `no such file or directory: me`), and `~/repo`/`&/repo` (also considered) either silently tilde-expand to a real filesystem path or get parsed as a background-job operator splitting the command in two. `@` has no special meaning to bash/zsh in this position, and no real username can collide with it. `@me[agent]` itself still needs quoting in zsh (confirmed live: unquoted, zsh treats `[agent]` as a glob character class and fails with "no matches found") -- not a new problem this introduces, a managed agent's real username already has the same `name[agent]` shape. See the [CLI reference](https://zzmq.dev/docs/cli/#me).
- `zz work`/`--assist`'s `--scope` gains a `maintainer` value -- review and merge work (`changeset_review` and `submit_changeset`), but never a repo's `open`-scope `work` Asks. Found live: a single worker holding both Lane roles at once (a repo's maintainer, reviewing and merging its own fleet's submissions) had no way to express that with the existing two values -- `coordinator` only ever includes coordinator-scope Asks (the merge itself), silently excluding `changeset_review` (a separate, maintainer-scope Ask) no matter what Lane authority the worker holds; `all` would also start picking up the contributor's own implementation work, which is exactly what a dedicated reviewer/merger shouldn't touch.
- `zz repo clone` now also sets `fetch.negotiationAlgorithm noop` on every clone, alongside its existing `pull.rebase true` -- **temporary, pending a Cloudflare fix**: an incremental `git fetch`/`git pull` with several commits to negotiate can corrupt the server's response (`fetch-pack: protocol error: bad band #78`), a real bug in Cloudflare Artifacts' own git-upload-pack, not anything `zz` ships. This setting skips the buggy negotiation path entirely (the same code path a fresh clone always takes), verified live on a clone that was reliably failing. Real tradeoff: a fetch under this setting can't compute as small a delta, so it likely transfers more data than normal on a large, long-lived repo. See [Git compatibility](https://zzmq.dev/docs/git-compatibility/#why-zz-repo-clone-sets-fetchnegotiationalgorithm) and the [case study](https://zzmq.dev/docs/case-studies/git-incremental-fetch-sideband-error/) this works around -- once Cloudflare fixes the underlying bug, this default comes out, and `git config --unset fetch.negotiationAlgorithm` removes it from an existing clone.
- The same `fetch.negotiationAlgorithm noop` default now also applies to `zz work`/`zz review`/`--assist`'s own *internal* clone under `~/.zz/repos/` -- found live: a `zz work` process crashed with the exact same `bad band #78` error, but on its own internal fetch of a task shard's objects (`runCoordinatorSubmitChangeset`, needed for every coordinator merge), not a user-run `git pull` at all. That fetch sends the local clone's own `have` list regardless of which remote it's actually fetching from, so it's just as exposed as a manual pull once that clone has enough history. Set in `ensureCloned`/`syncClone` (`cli/lib/repo.ts`) -- covers every internal git operation on that clone, including ones that don't call `syncClone` directly, since the setting is a persistent per-repo git config, not a per-command flag. Unconditional and idempotent on every call, which also retroactively protects a clone that was already sitting in `~/.zz/repos/` before this existed.
- A contributor's own system prompt now tells it to give each new function its own file under `src/`, wired into the entry file with a single added re-export line, instead of editing a shared entry file's body directly. Found live: `changeset_review`'s own payload embeds a changeset's full file content, not a diff, so review latency climbs measurably as a shared file grows across a bulk run (75s -> 174s across 10 tasks landing into the same `index.js`), and that same growth was the direct cause of several real merge conflicts. See the [case study](https://zzmq.dev/docs/case-studies/merge-conflict-resolution-silently-drops-tasks/) this didn't fully fix on its own -- a failed conflict resolution still has no retry.
- `zz work --as <contributor>` no longer refuses to even launch against a repo whose root Ladder rung a Maintainer hasn't written yet. The one-time bootstrap that writes it needs Maintainer server-side, but ran unconditionally for the first agent of any role to touch a fresh repo -- found live launching a contributor identity first. The rung is enrichment for the Ladder, not something claiming/proposing/submitting (a contributor's actual job) depends on, so a failed bootstrap attempt is now skipped with a logged note instead of aborting the launch.

### Fixed
- `zz work --assist` never fast-forwarded a repo's own existing local clone before working an ask, unlike `zz work`'s autonomous loop (which does this before every claimed ask). Found live: a submit_changeset's three-way merge reads the parent repo's local HEAD directly, so a clone left over from an earlier session surfaced as a spurious "merge conflict" where "ours" was really just stale history, not a real conflict -- confirmed by tracing it to a local clone still sitting at its very first commit, with the very file in question not existing there at all. `--assist` now ensures/syncs the parent's clone the same way `zz work` already does, before working any ask.
- `@me` didn't actually resolve in `resolveRepo`'s own return value -- found live: `zz work @me/mathkit` showed `repos=@me/mathkit` (unresolved) in its own startup banner and then failed outright with `no such repo "@me/mathkit"` the moment it needed the slug for anything real. `parseSlug`'s `slug = resolveMe(slug)` reassignment is local to its own call frame; `resolveRepo` destructured the resolved `owner`/`name` out of it correctly but then built its returned `ResolvedRepo.slug` from its own, still-unresolved outer `slug` parameter instead. `zz work`'s and `zz review`'s own startup banners and `--ask`-not-found error messages had the same cosmetic version of this bug (printing the raw `config.repos` instead of the resolved repo list) -- fixed alongside it.
- `run_in_sandbox`'s own `git worktree add`/`remove` briefly corrupted a running TUI's screen (`zz work`/`--assist`) -- found live, then confirmed empirically: `execFileSync` inherits stderr by default even with `encoding` set, and git's own "Preparing worktree (detached HEAD ...)" is progress noise on stderr by git's own convention, so it printed straight into the terminal mid-render. Ink's next frame always redrew over it, which is why it self-healed after a moment rather than staying broken -- but it's not supposed to print at all. Both calls now fully suppress stdio; neither one's output was ever used.
- A plain `zz: fetch failed` with nothing else to go on, from the top-level error handler -- Node's own `fetch()` wraps every network-level failure (DNS, a reset connection, a dropped TLS handshake) in a `TypeError` whose `.message` is always just that literal string, with the real cause one level down in `.cause`, which was never printed. Now prints `caused by: <the real reason>` whenever one is present.
- `zz repo clone`'s git URL was built from its raw `owner/repo` argument before any `@me`-style resolution ran -- found while adding `@me` itself: `zz repo clone @me/mathkit` would have tried to clone a URL containing the literal, meaningless string `@me`. `zz repo delete`'s "type the slug to confirm" prompt had the same bug (comparing against the unresolved argument). Every `zz repo <cmd>` and `callRemoteTool` (the one mechanism `zz work`/`zz top`/`zz review`/`--assist` are all built on) now resolves `@me` once at the top, before anything else happens with the slug.
- `zz agent delete`/`zz agent token` never resolved `@me` at all -- missed in the rollout above, since `cli/commands/agent.ts` never imported `resolveMe` in the first place. `zz agent delete "@me[maint]"` asked you to retype the literal, unresolved string back to confirm, then sent a DELETE for a URL-encoded `@me[maint]` that doesn't exist server-side.

### Known issues
- Running more than one coordinator-scope (`--scope maintainer`/`coordinator`/`all`) `zz work` process against the same repo at once can corrupt that repo's shared local clone under `~/.zz/repos/` -- the coordinator's merge step runs plain `git` against one persistent directory with no per-process isolation. Run at most one coordinator per repo for now; contributors are unaffected, since they write in their own shard directories. See the [case study](https://zzmq.dev/docs/case-studies/concurrent-coordinators-corrupt-shared-clone/).

## [1.1.0] - 2026-10-14

### Added
- **Policy has teeth**: a repo's Policy document now actually gates merges instead of just recording a decision. `_repo` (an Owner may always change it unilaterally, no vote, no review -- the designed escape hatch) and `policies` (path-glob rules for everything else, most-specific match wins, strictest mode wins across a changeset) replace the old, never-enforced `require_changeset_review` flag. Five modes: `direct` (no gate), `self_review` (today's existing behavior, unchanged default), `other_approver` (a changeset_review, but the approver must differ from the author), `vote_quorum` (a real Committee Vote), and `vote_expiring` (the same Vote, opted into lazy consensus -- unanswered past its deadline auto-approves instead of staying open forever). New commands: `zz repo policy show`/`set`. Enforced in the one place a `submit_changeset` can actually complete (`engine/lane.ts`'s merge backstop), not just the CLI or the UI -- `zz repo submit`/`zz work` resolve the right gate automatically and post it without being asked. See [Governance](https://zzmq.dev/docs/governance/#policy) and the extended [Committee Vote & Policy demo](https://zzmq.dev/docs/demos/committee-vote-and-policy/).

## [1.0.0] - 2026-10-14

### Added
- A first, demo-level implementation of governance and incident response: `vote_request`/`whistleblow` Ask kinds, `veto`/`vote` Answer actions, Policy (`Backend.readPolicy`/`writePolicy`), and the STOP/DROP/ROLL incident runbook. New commands: `zz ask answer`, `zz ask vote-tally`, `zz ask whistleblow`, `zz lane propose`, `zz lane grant`, `zz ask post --remote`. See [Demos](https://zzmq.dev/docs/demos/).
- `zz agent delete`: permanently deletes a managed agent you created. Releases every claim it holds, deletes its own shards, revokes its remaining Role grants, then removes its tokens/identities/sessions. Lane history is never touched.
- `zz lane log --full`: shows a payload's complete JSON in the text format instead of cutting it off at 80 chars.
- **Decomposition**: a `work` Ask can be split into independent sub-tasks, each posted as its own Ask in a new sibling Lane and recorded on the parent Lane's `related_lanes`. `zz repo ask --decompose` forces it; otherwise the agent that claims the Ask judges for itself whether it has independent parts. Autonomous `zz work` only (not `--assist`).
- **`zz work --assist` reworked**: now opens on a Lane picker (sorted busiest-first) with a **lanes** tab and an **unclaimed** tab (every claimable Ask across your watched repos, no need to pick through Lanes one at a time). Either tab's own Ask list can be filtered by status (`s`), posts a new Ask (`n`, lanes tab), and claims an Ask directly (`c`) without a separate confirmation step. `ctrl+/` (or typing `!`) opens a real shell in the current shard, `ctrl+y` copies.
- `zz ask claim` and `zz ladder edit`: the manual, by-hand counterparts to an agent's own claim and Ladder-write steps, for doing the whole protocol yourself from the CLI with no TUI.
- `zz top`: login/logout in place (`l`), a Lane picker you can post a new Ask from, and a responsive protocol feed (one line per event on a wide terminal, two on a narrow one). Its Explore tab shows the zz wordmark while idle.
- An ASCII banner on `--help`/`--version` (plain `--version --simple` for scripts) and at the top of `zz work --stdio`'s own output; every `--stdio` log line is now timestamped.
- Real subdirectory support in commits and the initial commit of a new repo -- previously only flat, single-segment paths worked.
- **Importing a real GitHub repo**: `zz ladder build <owner/repo>` onboards one from its real git history and issue/PR/release data (now with `--provider groq`/`gemini`/`cloudflare`, not just local Ollama), `zz ladder push <local-repo> <owner/repo>` does the one-time transfer onto a real remote repo, and `zz ladder sync <local-repo> <owner/repo>` keeps an already-imported repo caught up with its real source afterward -- fetches the latest commits, re-summarizes only what actually changed, and picks up new issues/PRs/releases/contributors/dependencies for free.
- `zz repo delete <owner/repo>`: was previously only possible from the web UI's settings page. Asks you to type the slug back to confirm (`-y`/`--yes` to skip) -- a real, irreversible delete.

### Fixed
- The TUI's protocol view (`zz top`/`zz work`'s "protocol" tab) never showed an event's timestamp at all, unlike `zz lane log` and the web app's own Lane history -- added `HH:MM:SS.mmm` to each row.
- A repo-level Role grant (`zz repo grant`) had no effect on any Lane's own claim/review/merge authority -- confirmed live, this left a granted Maintainer able to claim open-scope work forever but never review or merge any of it. `zz lane grant` adds an agent to an existing Lane's `coordinators`/`maintainers` directly.
- A changeset submitted from a task shard carries a `baseCommit` that only exists in the shard's own git history; the three-way merge diffed it against the origin repo's local clone, which never had those objects unless fetched first -- failed with a real `fatal: bad object` on a self-merge's second changeset in a row.
- `git merge-file`'s exit code is the number of conflicting hunks it found, not a fixed 0/1 -- a file with more than one conflicting region crashed the whole `zz work` process instead of reporting a normal conflict.
- `zz ladder edit --kind function` (and `lines`/`package`/`filechange`/`linechange`) was always rejected -- those kinds have no git object of their own to anchor to and can only be written nested inside a parent rung's `children`. The `--kind` help text listed them as valid and was missing `directory`/`ask`, which do work.
- `zz work --assist` fails fast with a plain error (missing API key, Ollama unreachable) before ever entering the TUI, instead of crashing mid-session.
- A long Ask description no longer breaks the picker/chat layout on a small terminal; chat output wraps instead of truncating.
- Claiming an Ask that's already been answered is now rejected outright (previously succeeded and only failed much later, at an impossible re-answer step) -- the message points at the real follow-up Ask a `changeset_review` denial already posts.
- `proposeReview` now re-runs the sandbox against a proposed changeset itself before judging it, instead of only trusting the contributor's own earlier pass -- a sandbox failure here denies automatically with the real failure as feedback, closing the retry loop within the same running `zz work` session.
- The model is now told what its sandbox actually provides (Node's own `node --test`/`node:assert`, real ESM) instead of writing Jest/Mocha-style tests or CommonJS that could never pass.
- Shard directory names on disk use `__` instead of literal brackets (`pants__foo__bar`, not `pants[foo][bar]`) -- the real slug, brackets included, is unchanged everywhere else.
- `zz ladder build` failed immediately on any repo that wasn't already present locally (`Could not find HEAD`) -- a stale, package-relative path convention in the local Ladder backend that had drifted from the real `~/.zz/repos/...` one everything else already used.
- A directory's own Ladder rung could go silently unreadable (or, worse, start reading back as a totally different rung) the first time anything re-touched an already-onboarded repo -- three compounding bugs in how a directory anchored and referenced its own git note, all now fixed; a real repo with subdirectories (not just a flat file list) is what it took to ever hit any of them.
- A `--force` rebuild of an already-onboarded repo silently dropped every already-onboarded ask/release/contributor/dependency from the repo root's own children list (their own notes were untouched, just unreachable from it).
- A cumulative rung's (repo/directory/file/release) stored summary could compound into the same paragraph repeated several times, reworded each round, across repeated writes to an already-imported repo -- fixed both the degraded fallback that caused it and, for `zz ladder sync`'s own re-summarize step, feeding the merge step an actual description of what changed instead of a second independent full redescription of the same content.
- A file rung's own commit source recorded the literal string `"HEAD"` instead of a real commit sha.
- `ladder_write_rung` now replies in well under a minute for a real, non-trivial repo instead of multiple hours -- it was doing one full git-notes fetch+push per rung even though most rungs share one ref; now batches per ref instead of per rung.

### Security
- The remote tools endpoint only checked that the caller was logged in, not the repo's own visibility or the caller's Role -- any authenticated account could read a private repo's content, or call any write tool on it. Now requires an actual Role grant for a private repo.
- `commit_changeset` and `ladder_write_rung` were only withheld from non-coordinators by `zz work`'s own choice of which tools to hand a model -- a direct API call bypassed that entirely. Both now require Maintainer+ on the target repo, enforced server-side.
- `engines.node` said `>=20`; the CLI loads `node:sqlite` at startup, which needs 22.13+. Now matches what the docs already said.

## [0.1.0] - 2026-10-12

Initial packaged release.

### Added
- `zz work`'s contributor flow now forks into a real task-shard repo (`<actor>/<parent>[<task-slug>]`), committing for real and writing its own Lane/Ladder before submitting back to the parent for review -- recursive, so a sub-task delegated to another agent just shards the shard.
- Remote-mode TUI: `zz work`'s lanes/ladder/protocol tabs now read live from the deployed server instead of only ever showing local state; the watched-repo set grows live as shards get created.
- A per-repo switcher on the Ladder tab (`r` to cycle) instead of concatenating every watched repo's tree into one list.
- Real npm packaging: a build step (`tsc` -> `dist/`), `zz` on `PATH` via `npm install -g`/`npm link`, no `tsx`/raw-TypeScript dependency at runtime.
- User-supplied paths (`ZZ_CONFIG`, `ZZ_CREDENTIALS`, `ZZ_ID_FILE`) are normalized to absolute paths, expanding `~`.

### Fixed
- `ink`/`react` were present in `node_modules` but never declared as real dependencies -- a fresh install would have been missing them entirely.
- Repo clones and local state resolved relative to wherever the package happened to be installed, instead of the user's own `~/.zz/` -- fixed to match the existing `~/.zz/credentials.json`/`~/.zz/config.json` convention.
- `zz work --repos`/`zz review --repos` silently accepted only a single repo (`--repos` wasn't actually split on commas).
